# 后现代极简 AI 工作台：开发态理想模型

版本 0.4.0；创建/修订：2026-10-30（北京时间）。状态：可执行的演进规格，尚非全仓库合格证明。

目标是让用户用少量必要操作，组合适合当前任务的 AI 能力，并理解实际结果及其条件。“集百家之长”通过可替换的功能、关系和组合实现；新增供应商、按钮或规则的数量不作为效果指标。界面简洁、能力充分、结果可信和成本可控分别评价。

## 1. 需求模型与具体场景

需求模型 N=(D, X, E, R, P, K)：D 为维度，X 为各维度的值域/适用范围，E 为维度间的依赖关系，R/P 为各自的奖励/惩罚函数，K 为经说明的必要条件。场景 S 指定具体环境、用户意图、输入、可用资源、授权、供应商/协议版本及实际依赖。

每个维度记录单位、方向、观测方法、未知值、依赖及评价类型。依赖边需写触发条件与作用，例如“图片文件可用”依赖返回、解码、交付，不能只画一条无语义箭头。

| 评价类型 | 奖励与惩罚语义 |
| --- | --- |
| 吸引子 / 排斥子 | 分别按声明方向接近 / 远离目标趋势评价；无限端使用单调方向，不计算到无穷大的数值距离 |
| 甜蜜点 / 苦涩点 | 接近某状态获得奖励 / 惩罚；反方向分别只意味着无该奖励 / 无该惩罚 |
| 正区间 / 负区间 | 区间内有奖励 / 惩罚；外部不自动成为惩罚 / 奖励 |
| 正花园 / 负深渊 | 指定区间外有奖励 / 惩罚；区间内保持对应中性 |

同一状态可同时有奖励与惩罚，保留向量 (R(x), P(x))，不默认互相抵消。偏好、未知、局部失败和硬条件分别表示；把某维度改成阻断条件，需要说明目标依据和适用场景。

工作台首批维度包括：任务完成、可见操作负担、参数表达能力、内容保真、凭据暴露、延迟、费用、可追溯性、状态复杂度、阅读/解释成本。阈值未测定时记为未知，不能为了全绿编一个数字。

## 2. 语句与限制的契约

每项关键判断可表示为 J=(目标, 场景, 前提, 观察, 推断, 策略, 证据, 复核触发)。代码注释、UI 文案、错误、测试名、README 和模块契约使用同一口径。

- 事实：实际看到了什么，如 HTTP 429、字段缺失、某次存档事务完成。
- 推断：事实在什么前提下支持哪项判断；仍可能有其他解释。
- 策略：本实现选择如何处理；记录收益、代价、替代方向和重新考虑的条件。
- 必要条件：为达成明确目标而成立的不变量，例如凭据不能交给本次授权范围外的目标。
- 实现范围：尚未接入的协议/字段；不据此推断上游或其他路线不可能支持。

“必须”“禁止”不是禁用词。审查的是约束是否有目标与条件依据。关键词扫描只能发现待读位置，不能代替判断。硬条件也不因文字变柔和而被绕过。

例：本地模板没有 max，只能推出“当前模板未覆盖”；HTTP 错误只能直接支持状态观察；字段叫 apiKey 不能单独证明值是秘密；一次模拟成功只支持该模拟条件下的观察。

## 3. 开发态构件

模块 M=(I, O, A, G, T, B, E, H)：输入/输出、条件假设、效果保证、状态迁移、复杂度预算、证据、最简宿主。每块有唯一实现来源、稳定 ID、版本、创建/更新时间。模块目标可以是直接功能、间接支撑或关系效果。

功能块计算局部结果；关系块管理具体连接、语义转换、授权绑定、状态归属；组合块管理完整任务及跨块进展。先按独立效果和证明责任拆分，再决定文件布局。把一个大状态对象从 app.js 搬到别处，或只增加转发文件，不自动减少耦合。

最简宿主提供完成目标必需的输入/环境和可观察出口，独立记录 ID、版本、时间、依赖、模式、判据与源码指纹。关系块的宿主要实际刺激并观察关系，例如同域错误路径不能获得规则匹配；纯函数的宿主无需整个网页。宿主少不等于证明弱，宿主多也不等于替代路线多。

### F/C/H/Q 分别成立

- F：明确证明对象、实现对应、假设、抽象边界、信任基和证明责任。证明预算由可检查状态/输入边界决定。没有证明产物就保持 UNKNOWN；测试、注释和哈希不能替代证明。
- C：当前宿主及目标场景实际满足所需条件。文档协议、账号权限、浏览器行为、真实调用分别留证。
- H：同目标、同观察语义、已独立达标的可行路线才进入比较池。预先固定途径编码向量 b，并计算 d_H(a,b)=Σ 1[a_i≠b_i]；源码编辑距离、包装数量和模拟器数量不算路线多样性，也不证明失败独立。
- Q：最低效果在声明场景内达成，同时满足相关必要条件。不存在的指标或样本不填 PASS。

整体准入需要四项证据都覆盖同一范围。候选入库、限定借用和实验可以先进行，不能因此宣称完整准入。有限状态模型的证明仅覆盖模型；JavaScript、浏览器和外部模型的全部行为没有因局部建模而自动得到证明。

## 4. 分解阻塞与组合

把阻塞写成最小失败条件：输入是什么、缺哪个条件、哪项效果未达标。分别实验补条件、换途径、换关系或改变组合。例如目标为 1 时，0+1 不可用，2−1 可成为另一候选；还要比较副作用、成本、状态与证据，不能只核对最后一个数。

| 关系 | 审查问题 |
| --- | --- |
| 做 / 反向做（1 / −1） | 是否改变目标方向？ |
| 做 / 不做（1 / 0） | 是否停止该效果而非生成反效果？ |
| 做 / 做得更好（1 / 1.000…） | 改进发生在哪个维度，是否引入其他惩罚？ |
| 做 / 等效做（1 / 2−1） | 在哪些观察、容差和条件下等效？ |

局部实验成功后再检验组合：假设相容、输出满足下一块前提、共享状态有归属、取消可传播、预算可终止、失败不会伪装成功。单块全通过不蕴含组合通过。

## 5. 运行态投影

开发态与运行态保持两条独立维护轨道。阶段 e 固定需求/条件允许范围、策略和指标，范围内不存在方向性漂移；一次提交不自动定义一个阶段。需求、协议条件或评价方向漂移时重新识别阶段。

运行产物 R_e=Π_e(D_e,S_e)。对每个允许场景 x，比较可观察行为 Obs(R_e,x) 与 Obs(D_e,x)：输出、错误、外部调用次数、授权目标、费用边界、保真及状态影响均在契约中指定。允许误差 ε 按维度定义；必要条件不靠其他奖励抵消。

运行态可以融合模块、专门化、生成代码或压缩；没有可读性目标，也无需解压回开发态。保留的是开发参考、投影方法/身份和该场景下的等效证据。R_e 与 R_(e+1) 不要求连续演进，分别对自己的开发参考验收。当前普通构建和缓存版本哈希只提供构建追溯，尚不是阶段投影等效证明。
