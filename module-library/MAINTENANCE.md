# 构件图书馆维护规则

规则版本：1.3.0。最近修订 UTC：`2026-10-29T09:10:00.000Z`。制定/更新日期：2026-10-29（北京时间）。适用于功能块、关系块、组合块、测试宿主、配方和证据；模块目录以 catalog.json 为唯一登记来源，宿主登记在 hosts/catalog.json。

维护目标是积累可重复使用、条件清楚、效果可追溯的构件。维护状态与验证状态分别管理；文件归档、测试通过、部署成功都不能替代完整开发态准入。

## 1. 分类、身份与责任

- 先按效果目标检索，再决定复用、升级、增加替代实现或新增目标。
- F / R / C 分别表示功能、关系、组合。关系块同样需要契约、独立入口和证据。
- ID 代表持续的构件身份，升级不改 ID，也不把旧 ID 分配给另一个目标。改名保留 ID；目标或观察语义根本改变时新建 ID，记录关联。
- 同一目标允许多种实现，每条途径单独登记条件和证据；只增加包装不计作新途径。
- 修改者负责明确效果、条件和变更范围；复核者负责核对契约、影响及证据。两项责任可以由同一维护者或当前执行 Agent 承担，不额外要求多人流程。
- 唯一实现源、借用入口和组合责任必须明确。共享状态、日志、凭据上下文、资源和副作用不能藏在目录外。

每次变更至少能回答：改了哪个 ID、为了什么效果、适用哪些条件、影响哪些使用者、如何验证、哪些问题仍未知。

## 2. 两条互不替代的状态轴

### 维护状态 lifecycle

| 状态 | 含义 | 使用规则 |
| --- | --- | --- |
| candidate | 候选构件，正在补契约和证据 | 可做研究与限定实验，不能宣称完整准入 |
| maintained | 有持续维护责任的构件 | 仍按其具体证据范围使用，不自动意味着 F/C/H/Q 全通过 |
| quarantined | 已发现会影响效果的缺陷或条件失效，暂时隔离 | 不纳入新的有效配方；保留反例和受影响范围 |
| deprecated | 已有迁移方向或决定停止推荐 | 既有固定版本组合可以保留，明确理由与迁移计划 |
| archived | 停止维护，保留追溯材料 | 不作为当前有效配方成员；复现使用对应历史快照 |

lifecycle 必须写明 reason。replacement 可以为 null；有替代指向时固定 ID 与版本。替代指向是迁移候选，不能证明两者等效。

允许的常见过程：候选 → 维护中；发现缺陷 → 隔离；修复与复核后 → 候选或维护中；停止推荐 → 弃用 → 归档。不是强制单向流程。恢复归档构件时也必须重新核对条件和受影响证据。

### 验证状态

F/C/H/Q 分别使用 PASS、FAIL、UNKNOWN、STALE。局部实验 local:PASS 是第五种独立记录，不升级四项准入。

- PASS：具体范围内有相应证据。
- FAIL：已有反例或实验未达标；不等于目标在所有途径下不可实现。
- UNKNOWN：尚无足够证据或门槛未定。
- STALE：旧证据因相关实现、契约或条件变化而不再覆盖当前情况。

candidate 可以有局部真实实验；maintained 也可能因条件漂移出现 STALE。隔离不删除已经发生的历史成功。

## 3. 入库要求

先建立模块卡与契约，再积累证据。至少包含：

1. 稳定 ID、类型、效果目标、版本、创建及更新时间。
2. 独立入口、唯一源码、输入输出、错误和终止/取消语义。
3. 条件假设、共享状态、副作用、允许场景和不保证的效果。
4. 最低效果、观察字段、样本与测量方式；未决定的参数保持未知。
5. 依赖的构件及准确版本、关系责任、验证用例、证据状态和限制。
6. 维护状态；弃用/隔离原因与替代指向（如果存在）。
7. 能承载该模块目标效果的最简宿主、宿主版本和时间。宿主必须能独立运行，说明条件、提供的环境、观察、判据及最简性依据；不能只是一份运行说明或只覆盖直接有用的功能。

不为了“全绿”补造证明、资源、阈值或成功候选。甜蜜点、区间等评价语义来自需求；奖励、惩罚、硬约束分开，不能在维护时无记录地改成单一分数。

首批构件保留 candidate：已有局部测试，但完整 F/C/H/Q 尚未通过。

## 4. 版本、时间和变更记录

模块版本独立于目录 schemaVersion、维护规则版本和仓库 package.json 版本。

| 变化 | 处理 |
| --- | --- |
| 不兼容的接口、效果契约或必要条件变化 | 升主版本；记录迁移与受影响组合 |
| 保持原契约的新增能力 | 升次版本 |
| 保持原契约的实现修正 | 升修订号 |
| 纯说明、标签、维护状态、补录依赖等登记变化 | 可保持实现版本，更新 updatedAt 并刷新相关证据 |
| 只重跑相同版本测试 | 不改模块时间；仅产生新的证据 recordedAt |

版本不可倒退。恢复旧实现时以新版本交付，记录恢复来源，不抹去中间历史。

createdAt 是第一次入库时间，升级时不改；updatedAt 不得倒退，升版必须使用更晚更新时间。存储为 UTC ISO 8601，列表按北京时间显示。历史由 Git 提交保留；PR 描述记录原因、影响、迁移、验证与未决项。

检查器会与已有本地证据中的模块修订信息比较，拒绝改写创建时间、时间倒退、版本倒退以及直接删除已有模块卡。首次建库或无旧修订记录时不能据此检查历史；这不是对完整 Git 历史的防篡改机制。不得通过删证据来掩盖不合规变更。

## 5. 依赖与配方

dependencies 记录效果复用所依赖的构件，采用准确 ID + version；不使用 latest 或模糊版本范围。它与源文件导入关系不同：效果依赖在目录登记，源码与共享文件变化仍受指纹检查。

- 不允许不存在的依赖、重复依赖、自依赖或静态循环依赖。
- 回调、反馈和递归放进组合契约，单独说明状态及终止/进展责任，不能靠循环依赖互相承诺。
- 配方 versions 固定组合实现及全部成员版本，覆盖声明依赖的传递闭包。
- 依赖升级时，逐层检查使用者的条件、错误、状态与最低效果，不能只改版本字符串。
- 静态引用有效不代表组合正确；组合仍需独立验收接口关系、归属、共享状态、取消/终止与整体效果。
- 普通构件不能继续依赖隔离或归档构件。必要时连同使用者及配方一起标为隔离；隔离/归档记录可以保留旧连接用于追溯。
- 弃用模块可保留在既有固定配方中；迁移后用同一目标契约验证替代，不能仅凭 replacement 指向切换。

首版目录每个 ID 只保存当前一版。历史版本在 Git 快照中复现；尚未提供同一目录多版本解析或自动下载安装。升级后要同步处理当前引用，或在旧快照中复现旧组合。

## 6. 证据维护与失效

本地证据绑定模块修订信息、输入文件指纹、执行环境、命令、统计和时间。record 必须实际运行成功才写入，失败不覆盖旧记录；旧记录保留不意味着当前版本仍通过。

schema 5 还绑定逐必需文件的结构化执行结果、源码 SHA-256、结果摘要、命令和模块归属。`module.tests` 是规范化相对路径的必需文件清单（拒绝 `./`、重复分隔符等路径别名）：每个文件单独启动 Node 测试进程，必须有至少一个实际测试用例，所有用例及套件均完成且无 fail / cancelled / skipped / todo；空文件的 Node 自动包装 PASS、空套件、缺失文件、重复或不完整结果不能获得 local:PASS。共享文件可属于多个模块，这只表示文件级覆盖，不声称每个用例只对应某个模块。

测试 stdout 不作为 TAP 证据解析。检查器要求带文件和源码位置的结构化 start/pass/fail 事件；不能提供这些字段的旧 Node（包括早期 20.x）会失败关闭，不能记录通过。本次实际验证环境为 Node 24.22.1。运行时清除继承的 `NODE_TEST_CONTEXT` 和 `NODE_OPTIONS`，避免父测试进程 IPC 或隐藏筛选选项替代明确登记的命令。

旧 schema 1/3/4 证据保留历史，但在新检查器中为 STALE，不能补造逐文件结果；评审后实际运行 `modules:record` 才迁移为 schema 5。全部必需文件通过且运行前后输入相同时，先校验待写记录确实可判为 PASS，再临时文件写入后原子重命名替换记录；任一失败保留旧记录原字节。结果、归属、统计、命令或源码绑定改变也使证据 STALE。未列入任何模块 `tests` 的可选 MCP 集成测试不属于此门禁，其可选 skip 不等于必需测试通过。


本地证据同时绑定宿主修订和模块—宿主版本关系。宿主代码、夹具、观测方法或判据变化，也会使相关证据失效。宿主的版本、创建时间、更新时间独立管理，适用同样的历史检查；不能只修改被测模块的版本来掩盖宿主变化。

默认宿主不得自动发真实 API 请求。local 记录本机实际效果；synthetic 明确外部条件由受控响应提供；live 才记录真实外部调用。真实模式按当前任务和调用条件执行，不能把受控响应写成真实生成成功。宿主是验证设施，不因数量增加就形成更多实现途径。

隔离模块仍可在宿主中诊断与复现实验；宿主结果包含维护状态，运行测试不自动恢复其准入。只校验该宿主与被测模块的绑定即可独立运行，不能把无关模块或完整网页变成局部测试的前置条件。

| 变化事件 | 需要检查的证据 |
| --- | --- |
| 源码、共享依赖或实现入口改变 | 对应实现证明、局部实验、所有受影响组合与投影 |
| 输入输出契约、最低效果、观测或容差改变 | 规格对齐、形式证明与效果实验 |
| 外部模型、协议、额度、权限、来源或 CORS 改变 | 条件证据、真实效果及组合；与该变化无关的证明不必无依据重做 |
| 替代池、途径编码或距离门槛改变 | H；共同目标与成功候选资格也要复核 |
| 仅刷新说明文字 | 检查是否改变语义；当前保守指纹仍要求刷新本地记录 |

首版对整个收录批次保守失效；尚无精细的语义影响传播。外部条件变化不会自动被源码指纹发现，需要维护者更新条件与状态。

真实实验记录时间、源码/部署身份（可取得时）、环境、模型、参数、样本、原始观察与结论范围；缺少的信息明确保留未知。成功一次不能提升为所有模型、参数或未来时点均可用。记录失败和未完成，不把 skipped 计作通过。

F 证据还需说明证明对象、实现对应、假设、信任基和预算。目录检查器不代替证明检查器；PASS 证据文件存在不意味着其内容正确。

## 7. 缺陷、隔离、弃用和归档

发现反例时，先记录触发条件、期望与实际效果、涉及版本；判断责任属于功能、关系、组合或外部条件。只隔离有依据的影响范围，并检查传递使用者。

修复需补充能区分修复前后的验收用例，复核相关假设。不能删除失败用例、调低最低指标或吞掉错误来恢复通过状态；需求确实改变时，应记录需求变更并重新对齐。

弃用说明原因、替代候选与现有使用者的迁移方式。没有替代实现也允许明确弃用，不能虚构替代路径。归档默认保留 ID、源码出处、最后版本、契约和历史证据；正常维护保留旧入口以便追溯。明确的删除需求另按其范围执行，先处理依赖与追溯影响。

## 8. 一次正常维护的操作顺序

1. 检索目标和模块，读取契约、维护状态及证据范围。
2. 列出受影响的功能、关系、组合与外部条件，保存最小反例或验收标准。
3. 修改唯一实现源；更新必要的版本、时间、依赖、配方和模块卡。
4. 独立实验后验证组合；根据实际结果填写 F/C/H/Q，保留未知与失效项。
5. 执行以下本地命令，最后检查 PR 中的变化与证据是否对应。

```sh
npm run modules:list -- --lifecycle candidate
npm run modules:record
npm run check
npm test
npm run build
```

record 只刷新已通过的本地实验，不自动选择途径、接受新需求、改变维护状态或提升 F/C/H/Q。超出当前任务的真实调用、发布等动作遵循已有任务范围；这些规则不额外增加逐次人工批准环节。

## 9. 自动检查与人工判断的边界

| 已接入检查 | 仍需实质判断 |
| --- | --- |
| 版本格式、时间格式和前后顺序 | 这次改动应升哪一级版本 |
| 基于已有记录的创建时间保留与版本不倒退 | 实现与需求语义是否保持 |
| 维护状态、依赖目标与准确版本、静态依赖无环 | 条件是否真实成立、共享失败依赖 |
| 配方版本、依赖闭包及隔离/归档引用限制 | 组合证明、真实整体效果与运行投影 |
| 文件指纹、测试实际执行、证据修订绑定 | 形式证明正确性、外部证据有效范围 |

日常复核优先由变更、故障、供应商变化或证据到期触发。需要定期复核的外部条件，应另定周期与费用范围；本文件不创建定时任务。

## 10. 开发态和运行态的维护边界

运行现场的新反例进入开发态修正规格、实现或投影，再验收新产物。维护库中的单调版本规则只用于开发构件身份管理，不要求运行产物从上一版本连续演进，也不要求从运行产物恢复开发库。

当前网页构建保持独立；新增目录和规则本身不证明运行产物已满足某个阶段。每次投影明确阶段条件、观察和最低效果，直接对对应开发参考验收。

## 共享模拟资源修订

- 资源登记入口：`module-library/test-resources/catalog.json`；协议与测试范围见各资源 README，不把模拟 PASS 升级为真实 API 已验证。
- 宿主可选 `resourceLock` 精确绑定资源、场景、fixture 集版本、fixture 哈希及协议快照；锁错或 fixture 文件变更未更新哈希时直接失败。
- 资源/宿主版本独立于模块生产契约版本。只修改宿主或 fixture 时升级相应宿主/资源，保持未改动的模块版本；模块卡引用变更仍更新 `updatedAt`。
- schema 4 本地证据增加 `resourceRevisions` 与运行起止时间；manifest/锁文件哈希一并绑定，不能用旧证据掩盖共享资源变化。资源创建时间与历史版本同样执行单调修订检查。
