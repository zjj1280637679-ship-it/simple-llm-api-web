# 构件 ID 与效果名称

本文件是模板，不是已收录构件。

入库和日常变更遵循 [维护规则](../MAINTENANCE.md)。填写 lifecycle（维护状态、理由、替代指向）和 dependencies（效果依赖的 ID 与准确版本）；维护状态不代替验证状态。

版本与时间以 catalog.json 中对应模块卡为唯一来源。首次入库填写 version、createdAt、updatedAt；升级保留 createdAt，按变化更新版本及 updatedAt。测试时间记录在证据 recordedAt，不能用它替代模块更新时间。

## 目标与来源

声明需求与场景；区分需求关系、环境条件、实现政策和待检验假设。

## 输入、输出与错误

列明接受域、效果判据、错误来源、必要诊断和不同成功级别。

## 条件、状态与副作用

声明共享状态、外部能力、资源、生命周期，未知条件保持 UNKNOWN。

## 保证与最低效果

明确假设下的保证；奖罚和硬约束分别记录。实验样本、阈值、测量、容差未决定时不得标 PASS。

## 形式证明

性质、实现到模型的对应、检查器、信任基、预算、证据路径；缺少证明时 UNKNOWN。

## 独立实验与反例

可独立运行的入口和用例、真实/合成条件、失败归属。单一路径失败不证明目标不可能。

必须绑定最简宿主的 ID 与版本。宿主登记自己的创建/更新时间、被测模块版本、所需条件、提供的状态或处理器、观察与判据、local/synthetic/live 模式和最简性依据。间接功能与关系功能同样需要可观察效果；宿主不得替被测模块完成其责任。

## 替代途径

共同目标、固定编码、候选数量、汉明距离、共同失败依赖。包装不是替代实现。

## 组合责任

接口前后置条件、关系归属、共享状态、取消/终止、结果归属和整体效果。

## 漂移与失效

源码、契约、场景或环境条件改变时，哪些证据变为 STALE，如何重新验收。

## 必需测试清单与局部证据

在模块卡 `tests` 中列出本契约所需的测试文件。每个必需文件须包含实际测试用例，且所有用例/套件完成、无失败/取消/skip/todo；不能用空文件、空套件或总批次 PASS 代替。共享测试文件明确模块归属；可选外部集成测试不混入必需清单。由 `modules:record` 实际生成 schema 5 逐文件证据，不手填 PASS；旧 schema 迁移与运行时要求见维护规则。
